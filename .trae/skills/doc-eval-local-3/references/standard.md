## 概述

本文档定义了一套用于评估开发资料文档易用性的评分标准。

- **评估对象：** 通用技术文档（API 文档、教程、指南、README、概念说明等）
- **评估目的：** 审计现有文档质量，输出具体改进建议
- **评分方式：** 三维度平均加权评分（完整性、正确性、易理解），总分 0-10

---

## 评分规则

### 评分制

- 每个维度独立评分，分值范围 0-10
- 加权总分 = Σ(维度分数 × 维度权重)，仅包含完整性、正确性、易理解三个维度

### 权重分配

#### 评分维度

| 维度 | 权重 |
|------|------|
| 完整性 | 33.3% |
| 正确性 | 33.3% |
| 易理解 | 33.3% |

### 总分计算

- 加权总分 = 完整性 × 33.3% + 正确性 × 33.3% + 易理解 × 33.3%

### 评分等级（统一标准）

| 评分 | 等级 |
|------|------|
| [0-2] | 不可用 |
| (2-4]  | 难用 |
| (4-6] | 可用 |
| (6-8]  | 易用 |
| (8-10] | 好用 |

## 评估维度详解

### 维度 1：完整性（权重 33.3%）

**核心问题：** 文档的内容完整，能指导开发者顺利使用，并包含参数说明、规格信息、版本配套关系等。

**评估子项：**

- 1.1 产品支持情况是否完整，包括软、硬件规格说明等
- 1.2 版本配套信息是否完整，包括上下游组件、OS等信息
- 1.3 参数/术语说明是否完整，包括参数的含义、取值、限制约束、使用场景、默认值和接口的返回值说明等
- 1.4 操作步骤是否完整，包括操作连贯性、执行结果、路径说明等
- 1.5 依赖/约束说明是否充分
- 1.6 错误码/告警是否完整
- 1.7 调用示例是否缺失
- 1.8 资源获取渠道是否完善

**评分标准：**

| 等级 | 分数 | 判定条件 |
|------|------|----------|
| 好用 | (8-10] | 内容完整，并提供约束、代码示例、故障案例，直接可用 |
| 易用 | (6-8] | 内容完整，但缺少约束、代码示例、故障案例，不影响使用 |
| 可用 | (4-6] | 内容存在部分缺失，存在模糊点需要实验验证，但可以接受 |
| 难用 | (2-4] | 内容不完整，需要额外查找才能完成 |
| 不可用 | [0-2] | 内容严重缺失，无法使用 |

---

### 维度 2：正确性（权重 33.3%）

**核心问题：** 文档内容正确，在使用过程中没有发现代码错误、描述或拼写错误、链接失效、代码示例错误等问题。

**评估子项：**

- 2.1 文档描述是否准确
- 2.2 链接是否有效
- 2.3 示例代码是否正确，有无语法错误
- 2.4 拼写是否准确
- 2.5 标点符号是否规范，包括单词、函数变量、函数名称、接口原型、目录和路径、参数、命令中有无多余的空格、中文文字间是否有空格、数字和单位之间有无多余的空格，英文段落中符号后是否漏掉空格，成对标点符号是否完整等；
- 2.6 安全敏感信息是否处理得当，包括个人数据、隐私数据、明文密钥、公网信息、局点信息、敏感词等
- 2.7 描述与回显/代码/命令的参数名称是否一致，缺省值与环境中是否一致

**评分标准：**

| 等级 | 分数 | 判定条件 |
|------|------|----------|
| 好用 | (8-10] | 整体无逻辑问题，按文档描述可一次性跑通 |
| 易用 | (6-8] | 存在非关键问题，稍作常识判断即可跑通，不影响使用 |
| 可用 | (4-6] | 存在非关键问题：需反复修改后才能跑通，但可以接受 |
| 难用 | (2-4] | 存在关键问题：需大量试错才能跑通，让人印象较差 |
| 不可用 | [0-2] | 存在严重问题，无参考价值，无法跑通 |

---

### 维度 3：易理解（权重 33.3%）

**核心问题：** 文档设计合理，符合开发者的实际操作习惯，文档表达清晰，章节和大纲分布合理。

**评估子项：**

- 3.1 术语解释是否清晰
- 3.2 文档描述前后是否一致，包括参数名称、专有名称、功能特性、规格、兼容性描述、图表内容等
- 3.3 文档架构/大纲是否易理解
- 3.4 是否有渐进式学习路径
- 3.5 文档内容是否容易理解
- 3.6 是否有冗余内容
- 3.7 代码片段命名与格式是否清晰易读（变量/函数命名是否语义化、缩进是否规范）

**评分标准：**

| 等级 | 分数 | 判定条件 |
|------|------|----------|
| 好用 | (8-10] | 文档设计合理，符合认知分层，容易理解，符合实际使用习惯 |
| 易用 | (6-8] | 文档设计合理，符合认知分层，有一些术语、概念不理解，不影响使用 |
| 可用 | (4-6] | 文档设计不合理，部分步骤逻辑跳跃，但可以接受 |
| 难用 | (2-4] | 文档设计不合理，内容穿插，找不到关键流程，用起来费劲 |
| 不可用 | [0-2] | 文档设计混乱，内容杂乱堆砌，前后矛盾，体验痛苦 |

## 不同文档类型的评估侧重

评分标准适用于各类文档，但侧重点有所不同：

| 文档类型 | 关键维度 | 调整说明 |
|----------|----------|----------|
| API 参考文档 | 正确性、完整性 | 函数原型、参数说明、返回值、错误码的完整性和正确性至关重要 |
| 教程/指南 | 正确性、易理解、完整性 | 步骤式流程是关键；检查步骤是否可按序执行 |
| 概念/概述文档 | 正确性、易理解 | 概念解释清晰度和文档可定位性最重要 |
| README | 正确性、完整性 | 快速入门信息至关重要；检查安装、基本用法、完整文档链接 |
| 故障排查文档 | 正确性、完整性 | 错误信息、原因、解决方案必须具体且完整 |
